# Reception-Assisted Admission

## Goal

A receptionist can admit a patient identified by DNI, collect a structured clinical form, obtain a non-editable triage priority, and place the consultation in the same dynamic `EntradaCola` used by digital patients. This flow does not create or use `Chat`.

## Domain

- `Paciente.usuarioAuth` is optional for reception-created patients.
- Patient identity fields are stored on `Paciente`; `OrigenRegistroPaciente.RECEPCION` identifies local registrations.
- Existing digital patients are reused by matching normalized DNI against `Paciente.numeroDocumento` or `UsuarioAuth.numeroDocumento`.
- `SesionRecepcion` selects one assigned hospital. A receptionist may work in several hospitals but can have only one active session.
- `AdmisionRecepcion` stores the structured form and resulting triage JSON for audit.
- `ConsultaMedica.codigoLlamado` is an anonymous public code for the hospital screen.
- `IngresoColaService` is the shared entry point for both digital and reception flows.

## Flow

1. List hospitals assigned to the authenticated receptionist.
2. Resume the active reception session or start one for a hospital.
3. Search by normalized DNI.
4. Create an admission, reusing or creating the patient.
5. Complete the whole structured form.
6. Finalize once. `TriageFormularioService` classifies the form in one AI call, without conversation.
7. The receptionist cannot submit or modify priority.
8. The admission, consultation, and queue entry are finalized transactionally.
9. The response includes `codigoLlamado` and dynamic estimation.
10. An open admission can be resumed from its metadata or cancelled before finalization.

## Rules

- DNI is required and normalized to digits.
- New reception-created patients require name, surname, birth date, biological gender, phone,
  street, street number and postal code. Floor and email are optional; a blank email is stored as null.
- Personal data is stored on `Paciente`; the structured address is stored as its associated `Direccion`.
- Emergencies/NN patients are outside this administrative flow.
- A patient cannot have two active consultations.
- Patient lookup reports whether an active consultation exists and its current
  state, so reception can show the conflict before submitting a new admission.
  Admission creation still enforces the same rule authoritatively.
- A receptionist cannot have two active sessions.
- A reception session cannot close with unfinished admissions.
- Cancelling an open admission marks both `AdmisionRecepcion` and `ConsultaMedica` as `CANCELADA`,
  records `fechaHoraCancelacion`, and never creates a queue entry.
- Finalized and cancelled admissions are terminal and cannot be reopened.
- The hospital comes from the active session, never from the admission request.
- Specialty must belong to that hospital.
- A reception-origin patient stores a structured address with street, number,
  optional floor, city, province, and postal code. When an existing patient is
  verified during admission, the submitted address replaces the stored address.
- Priority is generated by the backend and is not editable by reception.
- The required `motivoConsulta` is the concise patient-language account of the
  main complaint. Additional symptoms are optional and must not duplicate that
  narrative merely to satisfy validation.
- Pain is a repeatable structured list (`dolores`) with location and intensity
  from 0 to 10. The classifier considers every entry and uses the highest
  intensity in its normalized result and deterministic fallback.
- If the AI provider fails, a conservative deterministic fallback classifies explicit alarm signs and severe pain.
- External AI calls have bounded connect/read timeouts. A stopped or stalled
  Ollama instance must reach the same deterministic fallback instead of leaving
  the admission request pending indefinitely.
- Reception classification performs a single provider attempt; Spring AI's
  exponential retry policy is disabled so the fallback is reached promptly.
- `EntradaCola` remains the queue source of truth.

## Endpoints

```http
GET /api/recepcion/hospitales
GET /api/recepcion/sesiones/activa
POST /api/recepcion/sesiones
POST /api/recepcion/sesiones/{sesionId}/cerrar
GET /api/recepcion/pacientes/{dni}?sesionId={sesionId}
POST /api/recepcion/admisiones
GET /api/recepcion/admisiones?sesionId={sesionId}
GET /api/recepcion/admisiones/{admisionId}
POST /api/recepcion/admisiones/{admisionId}/finalizar
POST /api/recepcion/admisiones/{admisionId}/cancelar
```

The admission list returns only open admissions for the active session, ordered by
`fechaHoraInicio ASC`. Detail responses expose patient, hospital, specialty and terminal-state
metadata, but never the stored clinical form or raw triage JSON. For a finalized consultation
that remains `EN_COLA`, detail retrieval recalculates the current dynamic estimate.

Reception endpoints use `400` for validation, `403` for ownership/role violations, `404`
for missing reception resources, and `409` for active-consultation or invalid-state conflicts.
